# Logs Observer

Поиск и анализ логов через MCP-сервер `victorialogs` (`mcp-victorialogs`).

## Trigger Conditions

Активируй скилл, если в запросе есть слова или смысл:
- лог, логи, logs, log
- посмотреть логи, проверить логи, найди в логах
- ошибка / инцидент / падение сервиса по логам
- что происходило в системе, почему упало, когда началось

## Workflow

1. Вызови `collect_context` с текстом запроса пользователя.
   - Если `missing_fields` непустой — задай уточняющий вопрос и остановись.
   - Извлечённый `time_range` используй для всех последующих запросов.

2. Определи структуру логов:
   - Вызови `field_names` чтобы узнать доступные поля.
   - При необходимости вызови `streams` чтобы найти нужный поток.
   - Вызови `field_values` для уточнения значений ключевых полей
     (service, host, level и т.д.).

3. Выполни основной поиск:
   - Вызови `query` с LogsQL-запросом, используя временной диапазон
     из `collect_context` (дефолт: `now-15m .. now`).
   - Если нужна агрегация по времени — вызови `hits`.
   - Для среза по полям — вызови `facets`.
   - Всегда делай запрос с корректным диапазоном времени (`start`/`end`) и
     лимитом (`limit`) для просмотра реальных записей.

4. Оцени достаточность данных:
   - Если результатов нет, перед уточняющими вопросами сделай fallback:
     1) ослабь фильтр области (убери слишком узкие поля `service/namespace`);
     2) оставь только severity + time range;
     3) вызови `facets` по ключевым полям (`service`, `cluster`, `namespace`),
        чтобы понять, где есть данные;
     4) повтори `query` с обновлённым фильтром.
   - Только если после fallback данных всё ещё нет — задай уточняющие вопросы
     (см. Clarification Policy).

5. Сформируй отчёт:
   - Вызови `format_logs_report` с найденными данными.

## Time Range Rules

- Если пользователь указал диапазон (`10:00-10:30`, `за последние 2 часа`,
  `с 14:00 до 15:00`) — используй его.
- Если диапазон не указан — дефолт: **`now-15m`** (последние 15 минут).
- Если диапазон неоднозначный (`утром`, `недавно`) — уточни конкретные
  границы времени у пользователя.
- На короткие ответы вида `за 1 день` / `за 2 часа` сохраняй контекст
  предыдущего запроса (фильтры по cluster/service), а не начинай поиск с нуля.

## Clarification Policy (обязательно)

Если не хватает данных для точного поиска, **всегда** запроси недостающее.
Минимальный список того, что можно уточнить:
- сервис / компонент (где искать)
- окружение (`prod` / `stage` / `dev`)
- временной диапазон (если нужен точнее дефолта)
- идентификаторы: `trace_id`, `request_id`, `user_id`, `order_id`, `pod`, `host`
- ожидаемый симптом: текст ошибки, код ответа, статус

Пример уточняющего сообщения:

> Недостаточно данных для точного поиска. Уточните, пожалуйста:
> сервис, окружение и период (сейчас использую последние 15 минут).

## MCP Usage Rules

- Используй MCP-сервер `victorialogs-mcp`.
- `query` — основной поиск логов (LogsQL).
- `hits` — агрегация количества логов по интервалам времени.
- `facets` — топ значений по полям (срез/факторизация).
- `streams` — список потоков логов.
- `field_names` — доступные поля в логах.
- `field_values` — значения конкретного поля.
- `documentation` — встроенная документация по LogsQL и API.
- Если синтаксис запроса неизвестен — вызови `documentation` для справки.

## Report Format

Отвечай кратко и структурно:

### Период поиска
Явный или дефолтный (15 мин).

### Что найдено
Ключевые события, ошибки, частота, паттерны.

### Гипотеза причины
Если данных достаточно для предположения.

### Что нужно уточнить дальше
Если уверенность низкая — перечисли, что запросить у пользователя.

## Safety and Accuracy

- Не выдумывай данные, которых нет в логах.
- Если релевантных записей нет — явно так и скажи.
- Если вывод неполный — пометь это и запроси недостающие параметры.
- Не выполняй запросы без фильтров на больших объёмах — используй
  временные рамки и фильтры по полям.
